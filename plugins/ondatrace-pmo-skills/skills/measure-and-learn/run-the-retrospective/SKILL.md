# Run the Retrospective

Most retrospectives produce the same five platitudes ("communicate early", "involve stakeholders"). A useful one tells the next PM something specific that happened here and what they should do differently because of it.

## Inputs to ask for

- The charter or original goals and dates.
- What actually happened: status history, milestone changes, risks and issues raised, decisions and change requests, what was delivered and accepted.
- Closeout notes, team feedback, sponsor comments.

## Rules

- **Never invent a figure, date or name** not in the material.
- **Plan vs actual first.** Compare the original dates, scope and budget with what happened, with the arithmetic.
- **Interventions: did they help?** For each significant decision or change, what was expected and what the evidence shows happened. Don't claim cause where the evidence only shows sequence.
- **Lessons: three to six, sharp and specific.** Each one tied to something that happened on this project, written as advice to a PM inheriting a similar one. If the history is too thin to say anything specific, write fewer, not generic ones.
- **What to repeat** matters as much as what to fix.

## Output

```
# <Project> retrospective

**Plan vs actual**
| | Planned | Actual | Difference |
| --- | --- | --- | --- |
| Finish | ... | ... | ... |
| Scope | ... | ... | ... |
| Budget | ... | ... | ... |

**What happened** (a short paragraph)

**Decisions and whether they helped**
- <decision, date>: expected <x>; evidence shows <y>. <Helped / Didn't / Unclear>.

**Lessons for the next PM**
1. <specific lesson> (because <what happened here>)

**Repeat**
- ...
```

## Learn from corrections (user-controlled)

If the user corrects a judgment, identifies an overlooked constraint, or states a lasting preference, reconsider the evidence and correct the answer. Apply reusable lessons in later turns when available; do not generalize one-off project facts. Ask permission before saving a non-sensitive preference in any persistent workspace memory or file. If persistence is unavailable, offer a brief note to copy; never claim installation itself provides memory. Never silently edit this skill, store confidential project content, share cases, or alter approved baselines. Do not solicit feedback after every successful answer. Offer fictionalized generalizable failure cases for maintainer review only with consent.
